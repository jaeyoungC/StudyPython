# 38 — 에이전트의 원리

## 목표

코딩 에이전트(coding agent)가 내 저장소를 어떻게 읽고, 무엇을 기억하고, 왜 가끔 엉뚱한 곳을 고치는지 **구조로 설명**할 수 있게 됩니다.
한 세션을 관찰 기록표에 남기고, 그 기록에서 "이 에이전트가 지금 실패하고 있다"는 신호를 읽어 냅니다.

## 노트와의 연결

노트는 챗봇에 기대어 코드를 짜는 습관의 함정을 짚으면서 이렇게 말합니다.

> "코드베이스 검색, 컨텍스트 윈도 관리, 도구와 MCP 서버가 컨텍스트에 주는 영향, 서브에이전트의 상호작용, 하네스가 LLM을 감싸는 방식을 알면 에이전트를 더 잘 이끌고 실패를 알아챈다"

15단원부터 매 단원 작은 과제를 에이전트에게 맡겨 왔습니다. 이 단원은 그동안 "되는 것 같아서" 써 온 도구의 뚜껑을 엽니다.
구조를 알아야 39~42단원에서 스펙·컨텍스트 파일·권한·병렬 실행을 **의도적으로** 설계할 수 있습니다.

## 공부할 개념

| 개념 | 핵심 | 참고 |
| --- | --- | --- |
| 컨텍스트 윈도(context window)와 토큰(token) | LLM이 한 번에 볼 수 있는 입력의 상한. 내가 쓴 지시, 읽은 파일, 도구 결과, 모델의 답이 **모두 같은 창을 나눠 씁니다.** 창이 차면 요약(compaction)되거나 앞부분이 잊힙니다 | [Context windows](https://platform.claude.com/docs/en/build-with-claude/context-windows), [Token counting](https://platform.claude.com/docs/en/build-with-claude/token-counting) |
| 도구 호출 루프(tool-use loop)와 하네스(harness) | 모델은 텍스트만 냅니다. "파일을 읽어라"는 **요청**을 내면 하네스(에이전트 프로그램)가 실제로 읽어서 결과를 다시 창에 넣고, 모델이 다음 행동을 정합니다. 이 반복이 에이전트입니다 | [Tool use overview](https://platform.claude.com/docs/en/agents-and-tools/tool-use/overview) |
| MCP 서버와 서브에이전트(subagent) | MCP(Model Context Protocol)는 "외부 도구를 에이전트에 꽂는 표준 소켓". 서브에이전트는 별도의 창을 가진 또 하나의 루프로, 결과 요약만 상위 창에 돌아옵니다 | [modelcontextprotocol.io](https://modelcontextprotocol.io/) |

세 개념은 하나의 질문으로 묶입니다. **"지금 이 에이전트의 창에는 무엇이 들어 있고, 무엇이 빠져 있는가?"**
좋은 답과 나쁜 답의 차이는 대개 모델의 지능이 아니라 창의 내용물에서 납니다.

### 에이전트 루프를 손으로 그려 보기

```
사용자 지시 ─┐
CLAUDE.md ───┼─▶ [컨텍스트 윈도] ─▶ LLM ─▶ "Grep 'TaskService'" ─▶ 하네스 실행
도구 목록 ───┘        ▲                                              │
                      └────────── 검색 결과 3,000 토큰 ◀──────────────┘
                      (반복: Read → Edit → Bash pytest → ... → 최종 답)
```

도구 결과가 창에 **누적**된다는 점이 핵심입니다. 10만 줄짜리 로그를 `cat` 하게 두면 창의 대부분이 로그로 채워지고,
그 뒤의 판단은 내 지시를 거의 보지 못한 채 내려집니다. 노트가 "도구와 MCP 서버가 컨텍스트에 주는 영향"을 따로 꼽은 이유입니다.

### 코드베이스 검색은 어떻게 이뤄지는가

에이전트는 저장소 전체를 외우지 않습니다. `grep`·`glob`·파일 읽기로 **필요할 때 일부만** 가져옵니다.
따라서 이름이 일관되지 않은 코드(`get_task` / `fetch_item` / `load`), 거대한 파일, 설명 없는 설정값은 사람에게도 에이전트에게도 똑같이 비쌉니다.
15단원에서 계층을 나누고 24단원에서 테스트 이름을 읽히게 지은 것이 여기서 돌아옵니다.

### 토큰 비용은 어디서 새는가

- 같은 파일을 여러 번 읽기 (요약되지 않은 긴 세션)
- 테스트 전체 출력(`pytest -v` 수백 줄)을 매번 창에 넣기 → `-q` 나 실패만 보기
- 서브에이전트를 쓰면 상위 창은 가벼워지지만, 전체 토큰은 **늘어납니다** (요약 비용 + 중복 탐색)

노트: "아주 긴 자율 실행의 가치는 토큰 비용에 비해 과대평가돼 있다". 이 단원에서 그 문장을 숫자로 확인합니다.

## 스스로 답해 볼 질문

1. 에이전트가 `todo/service.py`를 읽기 전에 `grep`을 먼저 한 이유는 무엇일까요? 처음부터 파일을 다 읽으면 어떤 비용이 생기나요?
2. 컨텍스트 창이 가득 차서 요약이 일어난 뒤, 에이전트가 내 초기 지시 중 **어떤 종류의 문장**을 잊기 쉬울까요? ("하지 마라"류 vs "해라"류)
3. 서브에이전트는 상위 창을 아끼지만 전체 토큰은 늘립니다. 어떤 작업이면 그 거래가 이득이고, 어떤 작업이면 손해인가요?
4. MCP 서버 10개를 한꺼번에 연결하면 모델이 쓸 수 있는 도구는 늘지만 무엇이 줄어드나요?
5. 내가 쓴 `CLAUDE.md`(튜터 모드)는 창에서 몇 토큰을 차지하나요? 그 비용을 낼 가치가 있었나요? → 40단원

## 함정

- "에이전트가 저장소를 다 안다"고 가정하기. 에이전트는 **검색한 것만** 압니다. 검색어에 안 걸리는 파일(예: `scripts/legacy_fix.py`)은 존재하지 않는 것과 같습니다.
- 긴 세션을 계속 이어 가기. 요약이 몇 번 지나면 초기 제약은 흐려집니다. 작업 단위가 끝나면 새 세션을 여는 편이 싸고 정확합니다.
- 도구 결과를 검사하지 않기. 에이전트가 "테스트 통과"라고 말해도, 창에 실제 pytest 출력이 들어왔는지 확인하세요. 출력을 안 보고 말하는 경우가 있습니다.
- 하네스와 모델을 혼동하기. 권한 확인, 파일 쓰기, 명령 실행은 하네스의 일입니다. "모델이 삭제했다"가 아니라 "하네스가 삭제 권한을 허용한 상태였다"가 정확한 진단입니다.
