# 42 — 병렬 에이전트와 조율

## 목표

독립적인 작업 2~3개를 여러 에이전트 세션에 동시에 맡기고, 사람(나) 또는 상위 에이전트가 조율하는 방식을 경험합니다.
그 과정에서 노트가 말하는 네 가지 실패 유형(과잉 설계·검증 생략·조기 중단·위험 행동)을 **실제로 관찰**하고, 각 유형을 어느 단계(스펙·컨텍스트 파일·권한·검토)에서 막을 수 있었는지 짚습니다.

## 노트와의 연결

> "여러 에이전트를 병렬로 돌릴 때는 사람이나 상위 에이전트가 조율하고, 동시에 열린 세션 사이에서 내 주의력을 관리한다"

> "대표적인 실패 유형은 과잉 설계, 검증 단계 생략, 목표 전에 멈추기, 위험한 행동이다"

> "아주 긴 자율 실행의 가치는 토큰 비용에 비해 과대평가돼 있다"

병렬화는 "구현이 병목이 아니다"의 가장 눈에 띄는 형태입니다. 그러나 병목이 사라진 것이 아니라 **내 주의력과 검토 능력**으로 옮겨 갔습니다. 이 단원은 그 새 병목을 재 봅니다.

## 공부할 개념

| 개념 | 핵심 | 참고 |
| --- | --- | --- |
| 분할의 조건과 조율 | 병렬로 맡길 수 있는 작업은 **같은 파일을 건드리지 않고, 서로의 결과를 기다리지 않는** 것. 분할은 모듈 경계(15·22단원)를 따릅니다. 조율자는 작업을 나누고, 결과를 합치고, 충돌을 풉니다. 조율자가 사람이면 주의력이, 상위 에이전트면 토큰과 요약 손실이 비용 | 22단원 시스템 분해 |
| 주의력 관리 | 동시에 열린 세션은 저마다 "확인해 주세요"로 나를 부릅니다. 세션마다 **상태(대기 중·실행 중·검토 필요·완료)**를 보드에 두고, 검토는 한 번에 하나씩. 머릿속 전환 비용은 토큰보다 비쌉니다 | — |
| 네 가지 실패 유형 | **과잉 설계**(지금 규모에 없는 층·추상화) / **검증 생략**(테스트를 안 돌리거나, 돌렸다고 말만) / **조기 중단**(일부만 하고 "완료") / **위험 행동**(삭제·강제 푸시·테스트 수정·권한 밖 접근). 유형마다 **예방 지점**이 다릅니다 | 41단원 체크리스트 |

### 실패 유형과 예방 지점

| 실패 유형 | 보이는 모습 | 가장 싼 예방 지점 | 그래도 새면 잡는 곳 |
| --- | --- | --- | --- |
| 과잉 설계 | 요청에 없는 추상 클래스, 설정 옵션, 플러그인 구조 | 스펙 0절(세 줄 질문)과 2절(하지 않는 것) | 계획 검토 네 질문 ③ |
| 검증 생략 | "테스트 통과" 문장은 있는데 출력이 없음 | 체크리스트 중-2(판정 명령 제공) | 후-1 직접 실행 |
| 조기 중단 | 4단계 중 2단계까지 하고 "완료했습니다" | 단계마다 판정 명령 | 후-2 요구사항↔테스트 대응표 |
| 위험 행동 | `git push --force`, 테스트 삭제, `.env` 읽기 | **권한**(40단원) — 문장이 아니라 환경 | 승인 단계, diff 검토 |

위험 행동만은 컨텍스트 파일의 문장으로 막지 않습니다. 30단원의 원칙 그대로, "하지 말라"보다 "할 수 없게".

## 과제

작업 세 개를 고릅니다. 37단원까지의 시스템에서 **서로 다른 모듈**에 속한, 각각 30분 안팎의 것. 예:

- (a) `todo/ratelimit.py`에 클라이언트별 한도 설정값 추가 + 테스트
- (b) `notifier/`의 로그에 요청 id 전파(31단원 규칙) + 테스트
- (c) `web/app.js` 목록 화면에 "미완료만" 필터 추가

| 과제 | 하는 일 | 산출물 |
| --- | --- | --- |
| A. 분할 검증 | 세 작업이 같은 파일을 건드리는지 미리 확인(`grep`으로 겹치는 import·파일). 겹치면 작업을 바꿉니다. 각각 짧은 스펙(프로토타입 깊이, 39단원 C) | `worksheets/parallel-board.md` 0부 |
| B. 사람이 조율 | 세 세션을 동시에 열고 맡깁니다. 보드에 상태를 적으며 진행. 검토는 한 번에 하나. 각 세션에서 "확인 요청"이 몇 번 왔고 내가 전환한 횟수를 셉니다 | 보드 1부 |
| C. 상위 에이전트가 조율 | 같은 세 작업(브랜치를 새로 따서)을 **하나의 에이전트에게 "서브에이전트로 나눠서 하라"**고 맡깁니다. 상위 창에 무엇이 남는지, 합칠 때 충돌을 어떻게 처리했는지 기록 | 보드 2부 |
| D. 실패 유형 채집 | B와 C에서 네 유형이 각각 나타났는지 `worksheets/failure-review.md`에 기록. 안 나타난 유형은 "왜 안 나타났는가"(예방 지점이 작동했는가, 운이었는가) | 실패 검토표 |
| E. 비교 | B vs C: 총 시간, 내 주의력 전환 횟수, 토큰(알 수 있으면), 재작업량, 결과 품질. 노트의 "과대평가" 주장과 비교 | 보드 3부 |

## 스스로 답해 볼 질문

1. 두 에이전트가 같은 파일의 다른 함수를 고치면 git은 합칠 수 있습니다. 그런데도 "같은 파일을 피하라"는 이유는 무엇일까요? (의미 충돌 vs 텍스트 충돌)
2. 상위 에이전트는 서브에이전트의 **요약**만 봅니다. 어떤 종류의 실패가 요약에서 사라지기 쉬울까요?
3. 세션 세 개가 동시에 "확인해 주세요"라고 합니다. 어떤 순서로 보겠습니까? 기준을 하나 정해 보세요 (되돌리기 어려운 것 먼저? 막혀 있는 것 먼저?)
4. "조기 중단"은 에이전트가 거짓말을 한 것일까요, 아니면 내가 "완료"를 정의하지 않은 것일까요?
5. 병렬로 3개를 돌려 시간은 1/3이 됐는데 검토 시간은 그대로입니다. 전체 처리량의 상한은 무엇이 정하나요?

## 함정

- 의존 관계가 있는 작업을 병렬로 맡기기 (예: 스키마 변경과 그것을 쓰는 API). 하나가 끝나야 다른 것이 시작할 수 있다면 순차입니다.
- 보드 없이 머릿속으로 관리하기. 세 번째 세션부터 어느 세션에 무엇을 말했는지 섞입니다.
- 상위 에이전트의 "모두 완료" 보고를 그대로 믿기. 서브에이전트 결과를 **각각** 41단원 후-1·후-2로 검토합니다.
- 병렬이 늘 빠르다고 가정하기. 합치는 비용(충돌·재테스트·검토)이 작업 비용을 넘으면 순차가 빠릅니다.
