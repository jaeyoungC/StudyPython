# 39 — 스펙 작성

## 목표

기능 하나를 **세 줄 질문 → 요구사항 → 기술 설계 → 아키텍처 영향**의 순서로 적은 스펙(spec)으로 만들고,
프로젝트 단계(프로토타입 / MVP / 운영 중)에 따라 스펙의 깊이를 조절할 수 있게 됩니다. 이 단원의 스펙 템플릿은 52단원까지 그대로 씁니다.

## 노트와의 연결

노트의 중심 주장은 "병목의 이동"입니다.

> "엔지니어는 완성된 디자인을 받아 그대로 구현하는 역할을 더는 기대하기 어렵다. 스펙의 빈칸을 스스로 채우고, 스펙이 없으면 직접 써야 한다"

그리고 스펙의 출발점으로 세 줄 질문을 줍니다.

> "누가, 얼마나 많이 쓰는가 / 지연·비용·일관성 중 무엇을 우선하는가 / 되돌리기 어려운 결정은 무엇인가"

깊이에 대해서는 이렇게 말합니다.

> "계획의 깊이는 프로젝트에 맞춘다. 새로 만드는 프로토타입은 짧은 프롬프트로 충분하지만, 성숙한 기존 제품은 더 자세한 스펙과 검증이 필요하다"

38단원에서 에이전트가 "모호한 지시를 받으면 가정으로 빈칸을 채운다"는 것을 봤습니다. 스펙은 그 빈칸을 **내가 먼저** 채우는 문서입니다.

## 공부할 개념

| 개념 | 핵심 | 참고 |
| --- | --- | --- |
| 세 줄 질문 | 누가·얼마나(규모) / 지연·비용·일관성 중 우선순위(트레이드오프) / 되돌리기 어려운 결정(비가역성). 이 셋에 답하지 못하면 스펙이 아니라 희망 사항입니다 | 노트 "병목의 이동", 23단원 ADR |
| 요구사항·기술 설계·아키텍처의 분리 | **요구사항**은 사용자가 관찰할 수 있는 행동("마감 하루 전에 알림이 온다"). **기술 설계**는 어떻게(어느 모듈, 어떤 테이블, 어떤 API). **아키텍처 영향**은 기존 결정(ADR)과의 충돌·확장. 세 층을 섞으면 구현자가 요구사항을 바꿔 버립니다 | 15·22·23단원 |
| 스펙의 깊이 조절 | 프로토타입: 목표 + 하지 말 것 5줄. MVP: 요구사항 + 완료 기준 + 되돌리기 어려운 결정. 운영 중: 전체 템플릿 + 마이그레이션·롤백·관측 항목 | 노트 "워크플로", 36단원 |

### 좋은 요구사항의 모양

| 나쁜 예 | 왜 나쁜가 | 고친 예 |
| --- | --- | --- |
| "알림을 개선한다" | 관찰할 수 없음 | "마감일이 있는 미완료 할 일은 마감 24시간 전 ±5분 안에 알림이 1번 발송된다" |
| "빠르게 응답한다" | 숫자 없음 | "`GET /tasks` p95 지연 200ms 이하 (할 일 1만 건, 동시 사용자 10명 기준)" |
| "에러를 잘 처리한다" | 범위 없음 | "알림 서비스가 5초 안에 응답하지 않으면 완료 처리는 성공시키고 알림은 큐에 남긴다 (28단원 폴백)" |

### "되돌리기 어려운 결정"을 찾는 법

12단원(마이그레이션)과 36단원(릴리스)에서 배운 질문을 다시 꺼냅니다.

- 데이터 모양이 바뀌는가? (열 추가는 쉽고, 의미 변경·삭제는 어렵다)
- 외부에 공개되는 인터페이스가 바뀌는가? (API 응답 필드, 이벤트 형식, MCP 도구 이름)
- 사용자가 학습한 행동이 바뀌는가? (버튼 위치, 기본값)
- 돈이 나가는 결정인가? (LLM 호출 횟수, 저장 용량)

## 과제

| 과제 | 하는 일 | 산출물 |
| --- | --- | --- |
| A. 예시 읽기 | `examples/spec-due-reminder.md`(마감 알림 기능 스펙 예시)를 읽고, 세 줄 질문의 답이 요구사항·기술 설계에 **어떻게 반영됐는지** 화살표로 연결해 봅니다 | 예시 파일에 주석 |
| B. 내 스펙 1: 운영 중 깊이 | 37단원까지의 할 일 시스템에 **"반복 할 일(매주 월요일 등)"** 기능을 추가한다고 가정하고, `templates/spec-template.md` 전체를 채웁니다 | `specs/recurring-tasks.md` |
| C. 내 스펙 2: 프로토타입 깊이 | 같은 기능을 "주말에 혼자 써 볼 프로토타입"으로 만든다면 스펙이 몇 줄이면 되는지 써 봅니다. B와 나란히 놓고 무엇이 빠졌는지, 왜 빠져도 되는지 적습니다 | `specs/recurring-tasks-prototype.md` |
| D. 빈칸 찾기 | B의 스펙을 에이전트에게 주고 "구현 전에 질문할 것이 있으면 모두 적어라"라고 합니다. 질문이 나온 자리가 스펙의 빈칸입니다. 스펙을 고치고, 다시 물어 질문이 2개 이하가 될 때까지 반복 | 스펙 수정 이력 (PR 커밋) |
| E. ADR-0027 | "스펙 템플릿 채택"을 ADR로 남깁니다. 대안: 템플릿 없이 프롬프트만 / 이슈 트래커 양식 / 이 템플릿 | `docs/adr/0027-spec-template.md` |

과제 D가 이 단원의 핵심입니다. **에이전트의 질문 수는 스펙 품질의 측정값**입니다.

## 스스로 답해 볼 질문

1. "누가, 얼마나 많이 쓰는가"에 "나 혼자, 하루 10번"이라고 답하면 기술 설계에서 무엇을 **빼도** 되나요? (27단원 속도 제한, 19단원 캐시를 떠올려 보세요)
2. 요구사항에 "SQLite 테이블에 `recurrence` 열을 추가한다"고 쓰면 무엇이 문제인가요?
3. 스펙에 "하지 말 것(non-goals)"을 적는 이유는 무엇일까요? 38단원 과제 C의 "틀린 가정"과 연결해 보세요.
4. 스펙을 다 썼는데 에이전트가 여전히 질문을 합니다. 그 질문에 답을 **채팅으로** 하는 것과 **스펙 파일을 고치는** 것의 차이는 무엇인가요? (다음 세션, 다음 사람)
5. 같은 기능이라도 운영 중인 제품이면 스펙이 길어지는 이유를 노트의 문장 없이 내 말로 설명해 보세요.

## 함정

- 기술 설계부터 쓰기. "어떻게"를 먼저 정하면 "누가 얼마나"에 맞지 않는 과잉 설계가 됩니다 (42단원 실패 유형 1).
- 완료 기준을 "잘 동작한다"로 쓰기. 완료 기준은 **테스트 이름**으로 쓸 수 있어야 합니다 (`test_recurring_task_spawns_next_on_complete`).
- 스펙을 한 번 쓰고 안 고치기. 구현 중 바뀐 가정은 스펙에 돌아가 적습니다 (41단원 체크리스트 "바뀐 가정 기록").
- 프로토타입에 운영 수준 스펙을 쓰기. 깊이를 맞추지 못하면 스펙 쓰기가 싫어지고, 결국 스펙을 안 쓰게 됩니다.
